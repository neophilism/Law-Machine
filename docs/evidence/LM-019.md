# LM-019 typed bounded rule language

The first executable-rule boundary accepts **JSON data only**, with an exact v1 envelope and strictly allowlisted fields: version-pinned source references, trigger event, modal legal force, boolean guard, exceptions, a supported effect operation and public explanation key. No arbitrary script, SQL or uploaded code is executed. Effects are only validated here; actual transitions are reserved for the compiler/scheduler milestones.

Static guards support typed fact access, finite scalar literals, boolean conjunction/disjunction/negation, equality and numeric comparisons, plus explicit unknowns. Validation enforces declared fact types, limits on rule counts, nesting depth, number of expression nodes and string lengths, and explicit capability negotiation. A rule requesting an unimplemented operation is invalid.

The `evaluateRuleGuard` fixture helper uses three-valued logic. A missing fact is unknown rather than false; an unknown exception prevents a definitive eligible outcome. A literal text value of `"unknown"` remains an ordinary string rather than being confused with the missing-fact sentinel. The helper **never executes rule effects or calculates legal deadlines**.

Tests: `tests/unit/rule-language.test.ts` cover valid source-pinned rules, missing facts and exception semantics, mixed-type comparisons, unknown fact names, prohibited effects, extra/injection-like fields, forged source versions, unsupported schema, malformed JSON, and deep expression bombs.

No provider, database, document import execution, React, Node server or real legal claim is required. Security review is source-based and AI-led; it is not an independent human certification. Roll back through a checked revert, leaving executable simulation disabled until later accepted compiler/scheduler milestones. Require GitHub Actions `foundation` and `workspace` checks at the exact final head, including unit/type/lint, audit, production build and Chromium browser tests.
